# Контент Livosphere

Результат полного цикла — выбранный авторский продукт в приложении и APK для владельца. Сначала выясни, какой результат поручен сейчас: brief, художественный прототип, native-интеграция или полный цикл. Не превращай просмотр/идею в поручение на всю цепочку. Работа ведётся по-русски внутри текущей копии Livosphere.

## Вход и маршрут

Прочитай корневые `AGENTS.md`, `README.md` и относящийся к продукту checkpoint. Сохраняй явно переданные полномочия. Роли реализации/review и проверки определяет AGENTS, скилл не запускает дополнительных агентов или видимые задачи по собственной инициативе.

Установи вид продукта из запроса:

| Режим | Что создаём | Художественные стадии |
| --- | --- | --- |
| `widget` | Самостоятельные авторские часы S/M/L | Brief → HTML S/M/L → явный AP-HTML |
| `wallpaper` | Самостоятельные живые обои | Brief → статичная композиция → AP-IMAGE → HTML поведения → AP-HTML |
| `set` | Обои и часы с художественной связью | Применимые стадии обеих частей; принятый компонент можно переиспользовать по его точной ревизии |

Не требуй обои для часов, часы для обоев или повторный апрув неизменённой уже принятой ревизии. Отсутствующая часть — N/A с причиной, не PASS. Если режим неясен, уточни только его. Если не заданы идея/референс, получи короткий brief; можешь предложить варианты, но не обозначай свой выбор принятым владельцем.

Актуальные границы — [контракт контента](../../../_bmad-output/planning-artifacts/ux-designs/ux-Livosphere-2026-08-31/sets/CONTRACT.md) и [решение процесса](../../../_bmad-output/planning-artifacts/sprint-change-proposal-2026-09-17.md). Последующие явные решения владельца имеют приоритет. Сохраняются clock-only scope, S/M/L, четыре фазы новых обоев, движение объектов, power/reduced/off и применимые release gates. Смена этих требований — отдельное решение, не оптимизация по умолчанию.

## Один продукт — один workspace

Определи устойчивый ID, revision и выбранную область `widgets/<id>` или `wallpapers/<id>` внутри актуального UX workspace из README. Комплект дополнительно использует `sets/<id>/STYLE.md` для связей. Найди существующие файлы до создания новых; продолжай тот же прототип и журнал при правках.

Используй [шаблон brief](assets/brief.md), заполняя только применимые поля. Локальные DESIGN/EXPERIENCE/approval и art/preview принадлежат поверхности; технические manifest/exports/code — delivery-структуре. Не создавай второй sprint tracker или дубликат runtime registry. Сохраняй источник и права для внешних материалов, способ генерации и revision для авторского арта.

## Художественная работа

Перед дизайном загрузи локальный `ui-ux-pro-max` и указания выбранной области. Новое визуальное направление требует предусмотренного им design-system поиска с сохранением; design-system относится к выбранному контенту и не меняет hub tokens. Для создания/редактирования растрового арта используй доступный imagegen skill/tool; не заменяй его техническим placeholder под видом готового искусства.

- Для часов прочитай [widget route](references/widget.md). Сначала оцени выразимость выбранной идеи на существующем native clock механизме, затем показывай HTML S/M/L.
- Для обоев прочитай [wallpaper route](references/wallpaper.md). После AP-IMAGE опиши конкретные объекты и движения в HTML; не начинай с расширения fixture.
- Для комплекта используй оба маршрута только для порученных частей; STYLE связывает ревизии без runtime-синхронизации.

Создавай HTML по [заданию на review](assets/review.md). Согласование brief не равно AP-HTML. Перед переходом к зависимой стадии найди явное решение владельца на точную ревизию. Если его нет, предъяви конкретный результат для проверки, запиши checkpoint и дождись ответа; продолжай лишь независимую разрешённую работу. При правке принятого внешнего вида/поведения обнови revision и запроси приёмку изменённого результата. В полном цикле после получения нужного апрува продолжай уже порученную работу без нового вопроса «продолжать ли».

## Android и подключение

Перед native-изменением прочитай [интеграцию](references/integration.md), текущие SPEC/architecture и реальный код выбранных модулей. Проверь, какие возможности уже реализованы. Скилл автоматизирует работу агента с репозиторием; он не является renderer и не гарантирует новые эффекты без кода.

Переиспользуй lifecycle, настройки, фазы, clock provider/configuration и системные маршруты. Уникальные layout/renderer/assets остаются у продукта. Добавляй общий механизм только для принятой потребности этого продукта. Для ещё не поддержанного поведения сначала назови конкретный gap и ограниченное изменение внутри поручения; не начинай универсальный engine. Если native не может воспроизвести принятый арт, верни различие на художественное решение.

Контент входит в manifest/registry и каталог через поддержанный контракт. Никогда не обходи validator, не создавай dummy поверхность и не присваивай public/approved тестовым assets. В snapshot 17 сентября самостоятельная упаковка ещё требует реализации 13.3; проверяй её фактический статус перед подключением. Простое добавление папки пока не доказывает Android-интеграцию.

## Проверка и завершение

До кода запиши в текущем story/checkpoint закрытый список проверок: конкретные команды/selectors, ожидаемые результаты, сборка, native путь и условие завершения. Выбирай по затронутым границам; не копируй полный suite из старого отчёта. При UI проверь реальный путь и применимый checklist ui-ux-pro-max. Review и роль исполнителя — по AGENTS и выбранному режиму.

Передай [handoff](assets/handoff.md): где продукт в приложении, что сделать владельцу, APK/version/revision, выполненные проверки, ограничения и точный следующий шаг. Файл/HTML/emulator/физический телефон/магазин — разные evidence. Публикация и push не входят в создание контента без отдельного поручения.

В начале порученного цикла открой журнал этапов из handoff: получи текущее UTC время (`date -u +%Y-%m-%dT%H:%M:%SZ`), укажи поверхность/revision и область измерения (с нуля или доработка принятого продукта). При переходе между работой, ожиданием решения и исправлениями сразу добавляй отметку. В конце закрой последний интервал и посчитай сумму работы и ожидания; она должна равняться elapsed. Сборки/инструменты относятся к работе агента; это elapsed активного цикла, не CPU time и не оценка человеческих трудозатрат. Если точка пропущена, обозначь соответствующий интервал UNKNOWN; не восстанавливай её по git dates. Переиспользованный approval имеет ссылку и N/A нового ожидания. Запиши начало, художественные ожидания, активную работу, исправления и общий elapsed. Цель суток не разрешает сокращать принятый замысел. Повторяемость процесса подтверждается реальными циклами, не этим SKILL.md. После выполненного поручения остановись; следующий продукт, автоматизация по расписанию и дополнительный круг улучшений не запускаются автоматически.

## Примеры входа

- «Сделай отдельные минималистичные часы» → widget brief и HTML S/M/L; без обоев и AP-IMAGE обоев.
- «Оживи эту композицию» → проверить статус выбранного изображения; без AP-IMAGE предъявить его для принятия до зависимой работы.
- «Добавь второй принятый виджет» → проверить exact AP-HTML/native fit и доступность manifest contract, переиспользовать runtime, проверить изменённый путь; не создавать новую реализацию часов целиком.
