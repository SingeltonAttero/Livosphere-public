# Документация и дизайн в MR

В Livosphere GitHub Pull Request и Merge Request обозначают одну точку review. До создания MR автор проверяет влияние изменения на документацию и дизайн. Если меняется документированный контракт, соответствующие файлы обновляются **в том же MR**, до merge. Рассинхронизация кода, документации и принятого дизайна — blocker review.

## Что обновлять

| Изменение | Обязательные источники |
| --- | --- |
| Продуктовый scope, требования, сценарии, ограничения | Актуальные PRD/addendum и при необходимости SPEC/epics |
| Навигация, состояния, CTA, ошибки, accessibility | Спецификация экранов и применимые UX DESIGN/EXPERIENCE |
| Художественный вид или движение | Рабочий `.pen`, assets/provenance, связанная UX-спецификация и согласование точной ревизии |
| Архитектура, модели/контракты, schema, lifecycle | Architecture Spine / phone contracts и SPEC/decision, если их контракт меняется |
| Сборка, настройка агентов, signing/release процесс | BUILDING, AGENTS-SETUP, REPOSITORY-POLICY, HANDOFF и README по затронутой части |
| Статус story/приёмки | Единственный canonical sprint state; выполненные и неизвестные проверки не смешивать |

В MR перечисляются пути и ссылки на конкретные обновлённые документы; для дизайна — `.pen`-файл, node IDs/ревизия и статус принятия. При изменении planning-документов нужно пересобрать затронутый производный epic context; копия контекста не должна оставаться устаревшей.

Не требуется искусственно править документацию для каждого изменения кода. Если фикс восстанавливает уже описанное поведение, внутренний refactor не меняет контракт или изменение относится только к тестам, автор объясняет это в разделе «Документация и дизайн». Review проверяет объяснение. Отсутствие затронутых файлов не освобождает от оценки влияния. Для технического исправления native под уже принятый дизайн не нужно менять `.pen` ради галочки.

После принятия художественной ревизии код должен ей соответствовать. Новый художественный результат требует явного согласования автора; перенос неизменённых исходников не создаёт нового арт-апрува. При противоречии между принятым источником, кодом и дизайном фиксируется конфликт и решение владельца, а не молчаливое изменение всех трёх.

## Что говорит установленный BMAD 6.11.0

- [Build: загрузка контекста](../../.agents/skills/bmad-build/step-01-clarify-and-route.md) требует выбирать относящиеся к изменению PRD, Architecture, UX, Epics и Brief, чтобы не угадывать ограничения по коду.
- [Compile Epic Context](../../.agents/skills/bmad-build/compile-epic-context.md) прямо предписывает регенерировать epic context при изменении planning docs.
- [PRD: режим Update](../../.agents/skills/bmad-prd/SKILL.md) сверяет change signal с прежними требованиями и решениями и требует показать конфликты до применения.
- [Build: завершение](../../.agents/skills/bmad-build/step-05-present.md) обновляет spec/sprint state, создаёт локальный commit и предлагает PR; это не автоматический push.

В этих источниках нет универсального требования изменять `docs/` в каждом MR. Обязательное совместное обновление затронутой документации и дизайна — явно принятое правило Livosphere по поручению владельца. Installer-managed skills не переписываются: правило живёт в `AGENTS.md`, этом документе и PR template.
