# Пересмотр плана Livosphere

> Исторический baseline 9 сентября. Обязательная пара, порядок производства и предварительный rehearsal заменены [решением 17 сентября](sprint-change-proposal-2026-09-17.md); действующие AC и очередь — в [epics.md](epics.md) и [sprint plan](sprint-plan-phone-2026-09-09.md). Остальные неотменённые границы сохраняются.

**Результат сегодняшней работы — [восемь эпиков 8–15](epics-phone-themes-2026-09-09.md).** Этот документ объясняет перенос существующего задела и изменения канонических источников, необходимые перед разработкой нового направления.

## 1. Причина и полномочия

В [решении владельца 9 сентября](decision-2026-09-09-phone-themes-pivot.md) зафиксирован переход от одного набора для телефона/Wear OS к витрине живых обоев и виджетов часов Android-телефона. Причина — фидбэк о сложном использовании циферблата и недостаточной привлекательности тёмного тестового набора со скудной анимацией. Это качественная оценка владельца, не доказанная метрика рынка.

Первое поручение: изучить состояние и подготовить обновлённый набор эпиков. Последующее [явное принятие плана](approval-2026-09-09-phone-baseline.md) разрешило полностью выполнить миграцию документов и спринта. Уточнение «пока временно не будем» означает **отложить Wear OS с сохранением исходников и evidence**. Оно уточняет формулировку исходного решения «исключается из нового целевого результата» и не поручает удалять часовой код навсегда.

Выбран batch-режим Correct Course: владелец ожидает готовый пакет, технические детали уже делегированы исполнителю. Для объёма первого выпуска сохраняется явное PRD A-3 (прежнее локальное EPICS-A-1): один новый полный комплект плюс остальные готовые; фактический состав фиксируется до релиза. Ни сроки, ни десять тем не объявлены гарантированным результатом.

Направление и пакет приняты; PRD/UX/Architecture/SPEC и детальные stories обновлены в рамках явного поручения. Это не приёмка нового арта/физических результатов и не запуск production-кода или публикации.

## 3. Выбранный способ изменения

**Пересмотреть MVP и точечно адаптировать существующую реализацию.** Это major change по продуктовым требованиям и контрактам, при сохранении полезной Android-основы.

| Вариант | Оценка |
| --- | --- |
| Только скрыть Wear и переименовать старые stories | Недостаточно: не покрывает витрину, multi-instance widgets, новый art/motion, debug-only контент и release-contract. Усилие внешне малое, риск высокий |
| Откатить приложение к каркасу и строить заново | Не рекомендуется: теряется рабочий apply/lifecycle/build задел, подтверждений необходимости отката нет. Усилие высокое |
| Новый продуктовый baseline + адресные изменения | Рекомендуется: явно покрывает новый результат и сохраняет доказанный задел. Усилие среднее/высокое, главные риски локализованы в widgets, motion и выпуске |

Календарный риск — сочетание новой поверхности и ежедневного производства контента до конца сентября. Первая проверка AppWidget и первый полный комплект должны предшествовать обещанию темпа. Цель «сутки на комплект» относится к налаженному процессу, не к созданию всей платформы, восьми эпиков или реальной публикации.

### UX и процесс контента

Области: `hub`, `wallpapers/<id>`, новая `widgets/<id>`, `sets/<id>`. `watchfaces/<id>` сохраняет отдельную отложенную историю. UX-контракты обновлены в указанных областях; токены хаба сохранены, новые neutral planning mocks не являются принятым артом.

- `hub/DESIGN.md`, `hub/EXPERIENCE.md`: один набор → витрина; selector часов → phone widget; phone/watch diagnostics → сведения о телефонных поверхностях/экземплярах. Сохранить независимый визуальный язык, preview/главное действие, accessibility и отсутствие обязательной диагностики перед примеркой.
- `wallpapers/contour-draft/*`: существующие G1…G6 и запрет движения геометрии остаются правилами debug-«Контура», а не ограничениями всех будущих художественных сцен.
- `wallpapers/<new-id>/*`: новый локальный контракт объектов, четырёх фаз, уровней, реакций и остановки. Статичная картинка согласуется прежде HTML.
- `widgets/<id>/*`: самостоятельные DESIGN/EXPERIENCE, размеры, время/дата, работа host, per-instance selection и действия. Ни AOD Wear, ни WFF-возможности не наследуются.
- `sets/<id>/STYLE.md`: ссылки на обои/виджет и степень художественной связи; допускается отдельный красивый дизайн часов согласно решению владельца.
- Общая UX-карта и approval-индексы: новая topology с явной историей прежних approvals. Новый art/HTML/native имеет собственные ревизии и evidence.
- Новый навык производства: идея → статичная композиция → owner acceptance → HTML всех частей → owner acceptance → Android → emulator → APK владельцу. Конкретная реализация навыка относится к Epic 12.

Перед фактическим UX-дизайном использовать проектный `ui-ux-pro-max`, для нового визуального направления — `--design-system --persist --output-dir`, затем Compose-рекомендации и `pro-rules.md`. Этот план не подменяет их выполнение.

## 5. Проверенные платформенные факты и решения исполнителя

Источники проверены 2026-09-09. Это API/documentation evidence, **не запуск Livosphere AppWidget на устройстве**.

| Факт из первичного источника | Решение для плана |
| --- | --- |
| RemoteViews поддерживает ограниченный набор views, включая TextClock и AnalogClock; произвольные наследники не поддерживаются. [API](https://developer.android.com/reference/android/widget/RemoteViews) | Native clock widgets исследовать до согласования сложного HTML-арта; Compose хаба сам по себе не даёт произвольный widget renderer |
| `updatePeriodMillis` не допускает период менее 30 минут. [Обновление widgets](https://developer.android.com/develop/ui/views/appwidgets/advanced) | Не строить часы на минутных/секундных обновлениях provider; начать с host-rendered clock views и проверить реальное время/дату |
| TextClock имеет локализованные форматы времени/даты, 12/24-часовой режим и timezone. [API](https://developer.android.com/reference/android/widget/TextClock) | Базовый кандидат цифровых часов — TextClock; расписание обновления самого приложения не объявлять источником точного времени |
| AnalogClock присутствует в API, но отмечен deprecated; параметры/методы зависят от API level. [API](https://developer.android.com/reference/android/widget/AnalogClock) | Стрелочный вариант требует отдельного spike по нужной геометрии/ассетам и API 29+. Deprecated не означает невозможность, но готовность не обещается по HTML |
| `requestPinAppWidget` доступен при поддержке launcher; callback сообщает успешное pinning и ID, уведомление о неудаче не гарантировано. [Добавление](https://developer.android.com/develop/ui/views/appwidgets/discoverability) | Проверять capability, использовать пользовательское подтверждение и picker fallback; отсутствие callback не превращать в доказанную ошибку/успех |
| Системная конфигурация позволяет пользователю настроить widget при добавлении и позднее. [Конфигурация](https://developer.android.com/develop/ui/views/appwidgets/configuration) | Связывать настройки с экземпляром; проверить cancel, восстановление и сохранение при обновлении приложения |
| Доступность lock-screen host и условия показа зависят от OEM; запуск Activity может требовать разблокировки. [Android FAQ](https://android-developers.googleblog.com/2025/03/widgets-on-lock-screen-faq.html) | Обязательная device/host-проверка в Epic 11; штатный доступ там, где подтверждён. Не обещать универсальный LOCK и не подменять его screensaver |

Предлагаемые технические defaults, не слова владельца: три предопределённых уровня эффектов с полным составом на верхнем; per-instance widget preferences; фиксированные локальные границы четырёх фаз без location; отдельный service на wallpaper contribution с общим renderer. Точные значения и API-контракты исполнитель фиксирует в обновляемой архитектуре/спецификациях и проверяет до реализации соответствующих stories. Эти детали не создают новую очередь продуктовых вопросов.
