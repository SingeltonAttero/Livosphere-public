- (direction) Express distillation from the approved Livosphere PRD, approved UX workspace, approved Architecture Spine and technical research; preserve load-bearing detail through adopted companions rather than duplication.
- (decision) SPEC-livosphere adopts the approved PRD, UX integration and surface documents, technical research, and approved Architecture Spine as mandatory companions; it does not duplicate or edit them.
- (capability) CAP-1 — User can enter the hub, understand the current set, preview phone and watch surfaces, and navigate Theme, Devices and Settings independently; success is the approved skippable onboarding and honest preview path without false installation state.
- (capability) CAP-2 — User can launch the shortest available live-wallpaper preview/apply path and recover from cancellation, UNKNOWN, unsupported or policy-blocked outcomes; success requires explicit system confirmation and no false ACTIVE state.
- (capability) CAP-3 — Applied live wallpaper expresses the approved scene through time, battery, charging, swipe and tap behavior where supported; success requires lifecycle correctness, supported controls and the approved physical-device performance/power envelope.
- (capability) CAP-4 — User can read time, date and watch battery on the original Wear OS watch face in active and AOD states with the approved minimal accent; success requires WFF validation plus SP-02 emulator and physical-watch evidence.
- (capability) CAP-5 — User can acquire and manually activate the watch face through a validated channel while install, compatibility and active facts remain distinct; success requires SP-03/SP-04 evidence and honest UNKNOWN/fallback behavior.
- (capability) CAP-6 — User can independently control supported hub motion and wallpaper reactions, obtain contextual help, inspect product information and read meaningful in-app updates; success requires unavailable controls to be absent or explained and no remote push dependency.
- (capability) CAP-7 — Owner can build, validate, version and release the phone artifact and each resource-only WFF independently through a repeatable local contract; success requires a matching release manifest, checksums, validations and artifact-bound evidence.
- (capability) CAP-8 — Owner can add an approved visual set without redesigning hub features or copying shared engines; success requires one validated set manifest to generate registry, packaging and correct surface-specific resources.
- (capability) CAP-9 — Owner can evaluate the first release through a 20-day experiment report using store exports and voluntary feedback without embedded analytics; success requires resolved window/metric semantics and an evidence-based GO, ITERATE or NO-GO decision.
- (constraint) MVP is free and contains exactly one original techno-gothic set: one Android live-wallpaper surface and one Wear OS watch face; no second watch platform or broader surface promise.
- (constraint) Hub, live wallpaper and watch face are independent surfaces: phone artifact contains hub plus WallpaperService, while every WFF is a separate resource-only artifact coordinated by one set/release contract.
- (constraint) All AD-1 through AD-22 in the approved Architecture Spine are binding; their stable IDs and Deferred revisit conditions govern downstream design and implementation.
- (constraint) Preview, package installation, compatibility and ACTIVE are separate facts; UNKNOWN never means absent or failed, and returning from a system/store flow never proves success.
- (constraint) Hub UI tokens and motion remain independent of set art; wallpaper and watch face own separate readability, safe-area, reduced-motion, active/AOD and device-evidence obligations.
- (constraint) App-owned settings are local and typed; platform status is refreshed rather than persisted as truth. MVP has no backend, remote config, runtime catalog, product analytics or default outbound telemetry.
- (constraint) RuStore is the selected first release channel, but package/listing topology and the watch route remain gated by SP-03/SP-04; product logic stays store-neutral and a channel change requires owner approval.
- (constraint) Emulator, HTML/SVG preview and build success cannot produce device, battery, performance, AOD, OEM or store-delivery PASS; only versioned artifact-bound evidence can close the corresponding SP.
- (non-goal) No marketplace, large catalog, runtime plugin system, backend, user AI constructor, keyboard, broad widgets, iOS or multiple watch platforms in MVP.
- (non-goal) No runtime phone-watch synchronization, Watch Face Push, silent install or programmatic claim of watch-face activation in the baseline.
- (non-goal) No second set, universal wallpaper engine, hosted CI provider, remote telemetry provider or separate hub feature modules until their explicit revisit triggers fire.
- (decision) Success signal — after resolving experiment semantics and feasibility gates, a released set delivers working phone and watch surfaces through honest independent paths and supports an evidence-based 20-day GO, ITERATE or NO-GO decision against PRD SM-1 through SM-4 and countermetrics.
- (question) OQ-1/OQ-2 — What event starts the common 20-day window, which per-component metrics are available in the chosen channel, and what replaces SM-2 if it is not measurable? Resolve before experiment execution.
- (question) OQ-6 — Which exact phone, OS, launcher and watch builds form the supported release matrix? Resolve through inventory and SP-01 through SP-03 before compatibility claims.
- (question) Evidence gates — SP-01, SP-02, SP-03, SP-04, SP-06 and SP-07 remain UNKNOWN until their approved protocols run against matching artifacts; failure may narrow support or reopen architecture choices.
- (note) Wrapper-only content intentionally omitted: approval notes, review reports, editorial artifacts, generated mock galleries and workflow memlogs. Their accepted outcomes are represented by the canonical companion documents.
- (event) Self-validation coherence PASS: nine stable capabilities each have intent and success; constraints bend downstream choices; non-goals and concrete success signal are present; no unsupported assumptions were introduced.
- (event) Self-validation preservation PASS: all load-bearing PRD, UX surface, set style, architecture and technical-research content remains reachable through twelve existing adopted companions; wrapper-only process artifacts were intentionally excluded.
- (event) spec finalized
- (direction) 2026-09-09: owner принял Epics8–15 и всю миграцию через approval-2026-09-09-phone-baseline.md. Update выполняется из PRD0.3, новых UX/Architecture companions; прежний scope сохранён в архиве. Production не начат.
- (decision) CAP-4 и CAP-5 остаются deferred Wear с прежними stable IDs; не переименовывать в AppWidget. CAP-1/2/3/6/7/8/9 amended для phone; CAP-10 widget и CAP-11 starter collection — новые stable IDs.
- (capability) CAP-1 — intent: Пользователь выбирает локальные наборы, рассматривает обои и часы, проходит или пропускает знакомство. success: Витрина/preview показывают нужную ревизию и S/M/L; onboarding не задерживает CTA, повторяется не чаще недели только при подтверждённом неприменении; ACTIVE/UNKNOWN подавляют повтор. Изменение browsing не меняет установленные поверхности.
- (capability) CAP-2 — intent: Пользователь применяет выбранные живые обои кратчайшим подтверждённым системным путём и восстанавливается после отмены или ограничения. success: Примерка B не меняет уже применённые A при отмене; HOME/LOCK, совместимость и применение различаются. UNKNOWN/отсутствие handler/policy block имеют честный доступный следующий шаг без ложного ACTIVE.
- (capability) CAP-3 — intent: Установленные обои показывают живые объекты и четыре фазы суток с управляемой насыщенностью и уместными реакциями. success: Рассвет/день/закат/ночь зависят от местного времени, а не Android dark theme; authored objects/effects/levels проверяемы. Power/reduced/off и отдельный toggle tap/swipe соблюдаются; charging/offset только при поддержке; hidden/cold-start/multi-Engine корректны и quality budgets подтверждены отдельными проверками.
- (capability) CAP-6 — intent: Пользователь независимо настраивает движение, получает помощь и сведения о продукте и значимых обновлениях. success: Hub motion не наследует арт; неподдержанные controls скрыты либо объяснены. Новые темы приходят с app update, локальная история соответствует версии, повторные визиты не являются продуктовой целью; настройки обоев и каждого widget сохраняются.
- (capability) CAP-7 — intent: Владелец воспроизводимо выпускает телефонное приложение с проверенными наборами через RuStore. success: Phone release profile включает hub/wallpapers/widgets без Wear и debug-only content, signed artifact/revisions/hashes совпадают с tests и physical/store evidence. Постоянный ключ внешний, публикация отдельно разрешена; legacy candidate не объявляется новым.
- (capability) CAP-8 — intent: Владелец создаёт новые комплекты по повторяемому процессу и добавляет их без переделки общих функций. success: Идея → статичная композиция → явный апрув → HTML обоев и S/M/L с отдельными effects/фазами → явный апрув → Android → emulator → APK владельцу. Навык/шаблоны фиксируют provenance/revisions, ограничения HTML/native и длительность с ожиданиями; превышение суток не сокращает замысел и не прекращает работу без отмены.
- (capability) CAP-9 — intent: Владелец проверяет интерес и удержание и принимает решение о развитии на основе фактических данных. success: Пилот 5–7 внешних участников/7 дней и отдельное 20-дневное публичное окно имеют согласованный до сбора протокол. App installs, wallpaper uses, widget instances и самоотчёты разделены; SM-1≥100/20дней, новые пороги SM-5…7 не унаследованы от Wear; GO/ITERATE/NO-GO учитывает countermetrics и стоимость поддержки.
- (capability) CAP-10 — intent: Пользователь размещает авторские часы S/M/L, сочетает несколько экземпляров разных наборов и открывает выбранное приложение часов. success: S показывает время, M/L время+дату; время актуально без hub, учитывает locale/12–24/timezone. Pin/picker/config/cancel/restore/update/delete не смешивают экземпляры; target unavailable даёт повторный выбор. HOME проверен, LOCK исследован и реализован только при подтверждённом host, с системной аутентификацией.
- (capability) CAP-11 — intent: Пользователь получает стартовую коллекцию оригинальных принятых комплектов. success: Каждый включённый public комплект содержит обои и свои часы S/M/L, оба художественных approvals и native verification. Preview соответствует точной ревизии; Контур и fixtures отсутствуют в release. Десять тем — ориентир, first-release count определяется принятыми готовыми комплектами.
- (constraint) Новый baseline: Android phone min29/target36, несколько локальных бесплатных wallpaper+clock-widget sets, Wear deferred, Contour debug-only; no backend/account/paid checkout/runtime-download/plugins/broad widgets. Оригинальность, независимый shell, privacy и сохранённые phone quality budgets действуют.
- (decision) Adopt PRD0.3 + addendum, updated root/hub UX spines and phone surface contracts, Architecture AD1–26 + phone-contracts.md as mandatory companions. Эти source документы несут полные требования/детали, потому не считаются полностью absorbed audit-only sources.
- (assumption) PRD A-3: один полностью принятый новый комплект как planning floor, остальные по готовности; это локальный EPICS-A-1 переименованный без повторного использования прежнего PRD A-1. Финальный состав до релиза.
